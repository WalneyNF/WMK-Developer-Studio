Como usar agentes de IA para programar, criar e revisar código

Entenda o papel de Codex, OpenCode, Groq, Ollama, modelos, provedores e MCP. Aprenda a fazer a IA editar seus projetos com controle, histórico e testes.

Ver roadmapRepositório WMK

Nota de escopo: os trechos sobre o WMK descrevem módulos encontrados no código, não atestam uma integração Windows já validada. Os exemplos de tarefas são exercícios e não afirmam que o agente tenha executado as ações.

MÓDULO 01

O mapa completo: quem é quem

Imagine uma oficina. O modelo é quem raciocina; o provedor disponibiliza o modelo; o agente organiza o trabalho e usa ferramentas; a IDE é o ambiente onde estão seus projetos.

TermoExplicaçãoExemplo
Modelo de IA (LLM)Processa instruções, interpreta código e produz respostas ou chamadas de ferramentas.Llama, GPT, Gemini, Claude, Qwen
ProvedorDisponibiliza modelos por API ou serviço de autenticação. Tem limites, preços e credenciais.Groq, OpenAI, Google, OpenRouter
Executor localRoda um modelo no próprio computador, quando houver recursos adequados.Ollama
Agente de programaçãoRecebe seu objetivo, pede contexto, usa ferramentas, edita, testa e relata.OpenCode, Codex, Claude Code
IDEMostra arquivos, editor, terminal, diffs, depurador e integra o agente.WMK Developer Studio
ACPProtocolo de integração entre o editor e agentes.WMK ↔ OpenCode
MCPPadrão para disponibilizar ferramentas e fontes de dados a clientes e agentes.Agente ↔ ferramenta Git / banco
LSP / DAPServiços de linguagem e protocolos de depuração, não são modelos de IA.Autocompletar C#, depurar Godot
Você → WMK Developer Studio → Agente OpenCode → Provedor Groq → Modelo escolhido ↘ arquivos, Git, terminal e testes ↗ WMK ↔ ACP ↔ Agente | Agente ↔ MCP ↔ Ferramentas

Regra de ouro: contratar um provedor não instala um agente. Instalar um agente não fornece automaticamente créditos de API. Configurar MCP não significa criar uma IA.

MÓDULO 02

Quais tarefas os agentes realmente fazem?

Explicar

Entender um trecho difícil, documentar funções, explicar erros, comparar alternativas e ensinar padrões.

Criar

Gerar arquivos, testes, documentação, componentes, classes, rotas, telas e protótipos a partir de requisitos claros.

Modificar

Pesquisar referências no projeto, editar vários arquivos, refatorar nomes, corrigir bugs e atualizar chamadas.

Revisar

Ler diffs, procurar falhas lógicas, regressões, vulnerabilidades, lentidão e testes ausentes.

Testar

Executar comandos permitidos, ler logs, criar testes automatizados e tentar corrigir problemas encontrados.

Planejar

Converter uma ideia em backlog, arquitetura, etapas, riscos, critérios de aceite e tarefas menores.

O agente não substitui automaticamente o compilador, o depurador, os testes nem a revisão humana. Um texto convincente pode conter código incorreto.

MÓDULO 03

O ciclo certo de uma alteração

  1. Preparar: abrir o projeto e registrar um commit Git antes da intervenção.
  2. Definir: descrever problema, arquivos relevantes, comportamento esperado, restrições e critério de aceite.
  3. Investigar: pedir ao agente para localizar o código e explicar a hipótese antes de alterar.
  4. Editar: autorizar mudanças de escopo limitado, preferencialmente em worktree ou branch própria.
  5. Inspecionar: verificar o diff linha a linha, removendo alterações fora do escopo.
  6. Validar: executar testes, build, lint e teste manual do comportamento.
  7. Registrar: documentar o resultado e criar commit com a mudança aprovada.
Problema → Plano → Leitura de arquivos → Patch → Diff → Testes → Revisão → Commit
                                                ↖ erro? corrigir e testar de novo

Não confunda permitir o agente editar com aprovar o resultado final. Revisão posterior e autorização de ferramentas são controles diferentes.

Recomendação inicial: teste Codex como agente diretamente e OpenCode + Groq como segundo caminho. Assim você compara autonomia, custo, qualidade e facilidade de configuração.

MÓDULO 05

Instalar e configurar no Windows

Pré-requisitos

Ter o WMK Developer Studio compilado e funcionando, Windows com terminal PowerShell, Git e o CLI do agente instalado conforme sua documentação oficial. Não presuma que o instalador do WMK inclui Codex, OpenCode ou credenciais.

Passo A — Verificar o agente

# No PowerShell, depois de instalar o CLI escolhido:
codex --version
opencode --version

# Se o executável não existir, o PowerShell avisará.

Passo B — Autenticar

# Alternativa 1: Codex
codex login

# Alternativa 2: OpenCode
opencode
# Na interface do OpenCode: /connect
# Depois: /models

Os comandos /connect e /models são usados na interface do OpenCode, não como comandos do PowerShell. Escolha Groq no catálogo de provedores e insira sua chave na interface apropriada. Não compartilhe essa chave com o agente em mensagens comuns.

Passo C — Conectar à IDE

  1. Abra um projeto de teste confiável no WMK.
  2. Entre em Settings → Agents → Coding Agents.
  3. Selecione Codex ou OpenCode e confirme o comando executável.
  4. Crie uma nova tarefa pelo painel Agents.
  5. Comece pedindo uma explicação sem edição. Depois execute um teste de modificação pequeno.

O WMK possui definições nativas para codex app-server e opencode acp. A interface do fork ainda precisa ser validada na versão Windows WMK; nomes e disponibilidade de ações podem variar conforme o build.

Passo D — Testar Groq com OpenCode

  1. Crie uma chave no painel da Groq em conta própria.
  2. No OpenCode, execute /connect, selecione Groq e configure a credencial.
  3. Use /models e escolha um modelo disponível que funcione com ferramentas.
  4. Teste um arquivo de exemplo antes de permitir alterações em projetos reais.

Escolher Groq no OpenCode não significa que a interface WMK tenha hoje um seletor Groq próprio. A seleção acontece no agente, e a integração ACP transporta sua sessão.

MÓDULO 06

Exercício 1: primeira edição segura

Crie uma pasta descartável D:\Ferramentas\WMK-Teste-Agente e um arquivo calculadora.js:

export function dividir(a, b) {
  return a / b;
}

Peça ao agente:

Leia calculadora.js. Explique o que acontece quando b é zero. Não altere nada ainda. Sugira uma solução e dois testes automatizados.

Depois peça:

Agora implemente a proteção contra divisor zero. Modifique somente calculadora.js e crie calculadora.test.js. Mostre o diff e os comandos para executar os testes. Não instale dependências nem execute comandos destrutivos sem autorização.

Conferência: verifique se o agente definiu um comportamento consistente para divisor zero (erro explícito ou retorno documentado), se os testes incluem o caso normal e o caso inválido e se não alterou outros arquivos.

MÓDULO 07

Exercício 2: revisar seu código antes de publicar

Uma revisão útil precisa descobrir problemas concretos, não somente elogiar o código. Experimente este pedido:

Faça uma revisão do diff atual como revisor sênior. Procure: erros funcionais, segurança, condições de corrida, desempenho, compatibilidade, testes ausentes e possíveis regressões. Liste cada problema com arquivo, trecho, gravidade, evidência e correção recomendada. Não altere arquivos. Se não houver evidência, diga explicitamente que não encontrou problema demonstrável.

Segundo agente opcional: peça ao Codex para implementar e ao OpenCode para revisar. Não é garantia de correção: agentes podem compartilhar erros e alucinações. Mantenha testes e revisão humana.

Para revisão local do Git, use git diff e git status. O Codex também oferece a operação codex review no CLI; confirme as opções da versão instalada.

MÓDULO 08

Exercício 3: criar um minijogo do zero

Em vez de pedir “faça um jogo completo”, comece por um protótipo funcional com critérios mensuráveis.

Crie um pequeno jogo original HTML/CSS/JS de nave 2D na pasta deste projeto. Requisitos: controle WASD/setas, colisão, pontuação, reiniciar, tela ajustável, nenhum asset externo obrigatório. Separe index.html, style.css e game.js. Explique como executar, implemente testes para a lógica pura quando possível e não amplie o escopo sem registrar a decisão.

Em seguida, solicite: “Execute os testes disponíveis, examine mensagens de erro do navegador e corrija as falhas. Liste o que foi realmente validado e o que depende de teste manual.”

Para Godot, acrescente versão do engine, estrutura project.godot, cena principal, ações do Input Map e requisitos de GDScript. Para Unity e Unreal, diga a versão exata da engine e se o agente pode executar compilação pesada.

MÓDULO 09

Permissões e segurança (obrigatório)

Atenção: um agente com acesso a terminal pode apagar arquivos, executar código malicioso vindo de dependências, revelar segredos e sobrescrever mudanças. Use projetos de teste e permissões conservadoras.
  • Faça commit antes de começar e prefira branch ou worktree isolada.
  • Não conceda acesso automático a git push, rm, operações de banco destrutivas, comandos de instalação arbitrários ou leitura de arquivos secretos.
  • Não inclua .env, chaves de API, senhas ou dados pessoais no contexto enviado a modelos externos.
  • Para começar, use aprovação individual para escrita e execução, se o agente permitir.
  • Leia o diff antes de aceitar o código; valide com testes e compile.
  • Se o agente pedir para desativar antivírus, ignorar erros ou remover salvaguardas, interrompa e investigue.
  • Modelos rápidos não são automaticamente seguros para decisões sensíveis ou edição autônoma de grandes projetos.

Groq e limites: uma tarefa pode exigir dezenas de chamadas ao modelo; limites de requisições por minuto e tokens podem interromper a execução. Crie tarefas pequenas e configure controle de consumo.

MÓDULO 11

Como pedir melhor: modelo de contrato de tarefa

Copie a estrutura e complete apenas os campos necessários:

OBJETIVO:
[O que desejo que aconteça]

CONTEXTO:
[Projeto, engine e versão, linguagem, pasta, arquivos]

COMPORTAMENTO ATUAL:
[Qual erro acontece; logs e passos para reproduzir]

COMPORTAMENTO ESPERADO:
[O que deve acontecer depois da correção]

LIMITES:
[Não alterar outros módulos; não instalar dependências sem pedir]

EXECUÇÃO:
[Quais comandos pode executar; quais exigem aprovação]

CRITÉRIOS DE ACEITE:
[Build passa; testes passam; erro não reaparece]

ENTREGA:
[Resumo, diff, arquivos alterados, testes reais, riscos restantes]

Boa prática: para uma tarefa grande, peça primeiro somente análise e plano. Depois aprove cada etapa; por último solicite uma revisão independente.

MÓDULO 12

Perguntas de fixação e glossário rápido

  1. Groq é um agente que edita arquivos ou um provedor de modelos?
  2. Qual componente executa git diff: modelo, agente ou provedor?
  3. O que significa ACP? E MCP?
  4. Por que um diff revisado ainda precisa de testes?
  5. Qual vantagem de fazer commit antes da edição automática?
Ver respostas

1. Provedor. 2. Agente, por meio de ferramentas e permissões. 3. ACP integra agentes e IDEs; MCP integra ferramentas/fontes de contexto. 4. Porque alterações plausíveis podem introduzir falhas. 5. Permite comparar e restaurar o estado anterior.

Glossário: prompt = instrução; contexto = arquivos e informações usados na tarefa; token = unidade de processamento/cobrança; diff = diferenças entre versões; patch = alteração aplicada; commit = registro no Git; worktree = diretório de trabalho isolado do Git; sandbox = ambiente com limites; LSP = servidor de linguagem; DAP = protocolo de depuração.

Leituras e fontes

Documentação da base do fork: Agentes incorporados, Editor de sessões, Plugin de autocompletar.

Fontes externas: OpenCode — provedores, OpenCode — configuração e permissões, Codex CLI — comandos, Groq — limites de API.

Conferir documentação da versão instalada: interfaces, nomes de comandos e opções de permissão podem evoluir.
